# WO-0001 P0 capability probe — partial evidence

Status: **IN_PROGRESS**. This is development evidence, not independent P0 acceptance.

## Tested environment and scope

- Dates: 2026-10-02 to 2026-10-03 (America/Los_Angeles).
- Windows Codex Desktop package: `OpenAI.Codex 26.930.2377.0` during the original panel/source checks; `26.930.3930.0` installed when the `0.2.4` loader failure was diagnosed.
- Codex CLI / rollout `cli_version`: `0.157.0`.
- Probe plugin: `0.2.0` in the first restarted Desktop observation; repaired `0.2.1` in the second; `0.2.2` in the first current-thread source call; `0.2.4` failed to load due to an unsupported manifest field; `0.2.5` restored both placements and read-only current-chat access; `0.2.6` supplied a snapshot when the conversation-side panel opened. Version `0.2.7` is the current incremental-read candidate and has now been observed in restarted Desktop. All are portable local packages with one diagnostic skill, a bundled stdio MCP App, and a Node.js read-only scanner.
- Host: Windows; Node.js `v24.15.0` for the probe. No project-owned daemon, database, listener, network export, or Codex-file write. The MCP server is host-managed stdio and serves a small diagnostic view.
- One previously completed Codex Desktop turn from a local rollout was used. Its native IDs, path, prompts, commands, outputs, account metadata, and raw JSONL are deliberately omitted.

The installed package was listed by `codex plugin list` as enabled. A separate local app-server instance discovered its MCP tool/resource and `thread` entrypoint metadata. After a Desktop restart, `profiler.open` was available and returned successfully; the user screenshot showed a new `Profiler Panel Probe` content tab beside the conversation, but its body was blank. The Desktop log for that open reported `Uncaught SyntaxError: Failed to execute 'write' on 'Document': Invalid or unexpected token` during widget execution. A local syntax check reproduced the error: the build's string replacement expanded `$` sequences in bundled JavaScript and inserted duplicate HTML into it. Version `0.2.1` fixes the replacement, adds a global entrypoint at the user's request, and passes a bundled-script syntax regression test. After the second Desktop restart, the user confirmed the left-navigation entry and reported that opening it displayed the title and status text. The Desktop log recorded successful resource read and `mcp_app_sandbox.widget_running` for the fullscreen global view. A subsequent user screenshot showed the repaired `Profiler Panel Probe` tab rendered beside the conversation with the title and `MCP App opened by the host` status. This proves both supported placements render; it does **not** prove current-thread telemetry access. The screenshot is not committed because it includes unrelated Desktop content.

For `0.2.2`, the tested [Codex `rust-v0.157.0` app-server source](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/app-server/src/request_processors/mcp_processor.rs) adds `_meta.threadId` to direct MCP tool calls. The installed MCP SDK exposes request metadata to the server tool handler. A new `profiler.sourceProbe` tool accepts no thread ID as a model argument: it reads only the host metadata, validates the ID, verifies an exactly matching session header, and returns a content-free rollout summary. Local stdio integration tests pass for supplied request metadata and the missing-metadata case. An independent read-only call against this chat's active rollout matched the session and recovered a completed turn from an approximately 10 MB file in 200 ms, with 85 MiB one-shot process peak RSS. A real Desktop call returned `probe_version: 2`, `thread_context: provided`, `rollout_match: codex_home_unavailable`, and no turn summary. Thus Desktop-to-plugin current-thread metadata transfer **is verified**, while the plugin process lacked the rollout root. The tool does not update the UI or subscribe to live events.

The earlier [Codex `rust-v0.157.0` MCP configuration parser](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/codex-mcp/src/plugin_config.rs) inspection suggested `env_vars`, but that was the **wrong configuration boundary** for the installed Desktop plugin loader. After the user restarted with `0.2.4`, the left-navigation entry disappeared. The Desktop log reported `failed to parse plugin MCP server` and `unknown field env_vars, expected one of command, args, env, cwd`; a subsequent resource read reported `unknown MCP server 'panel-probe'`. This directly explains the missing entrypoint. The successful `codex plugin add` operation did not validate the runtime loader's schema.

Version `0.2.5` removes `env_vars`. When `CODEX_HOME` is absent, the bundled server derives Codex Home from its own `plugins/cache` installation path before verifying a matching rollout session header. This depends on the observed local cache layout and must be reassessed if packaging changes. A copied-bundle stdio integration test under a simulated install path passes with `CODEX_HOME` removed. After restart, the user's screenshot confirmed the global page rendered; its source check returned `thread_context: provided`, `rollout_match: not_found`. A direct tool call from this chat returned `rollout_match: verified` and a completed-turn summary; after opening the conversation-side tab, the user clicked its check button and reported `verified`. Therefore the read-only source path works in the chat context, while the global page cannot be assumed to select that chat. Version `0.2.6` sends the sanitized snapshot in the `profiler.open` result for immediate rendering beside the chat and retains a refresh button. After restart, the real chat-originating open returned `verified` with a completed turn and exact duration quality; the user confirmed the conversation-side panel displayed latest completed-turn duration, tool count, and input/output tokens **before Refresh**. The Desktop log recorded `mcp_app_sandbox.widget_running`. Ten local tests pass. This proves retrospective snapshot rendering; continuous live updates remain unverified.

Version `0.2.7` adds a bounded read-only JSONL cursor. Its first `profiler.open` call catches up to the matching rollout, retaining only active and latest-completed turn counters plus a byte cursor. Subsequent `profiler.progressProbe` calls read appended bytes; the visible panel requests them every five seconds and keeps a manual refresh control. A partial line is held in bounded memory until it becomes valid JSON. Records over 4 MiB are skipped and the affected counters/usage are marked unavailable. At that version, the one-shot `profiler.sourceProbe` remained a separate diagnostic; `0.2.8` removes it. Local tests pass. After restart, Desktop loaded the new tool list; a chat-originating open returned `verified`, active and latest-completed turn data, and zero skipped records. The user confirmed the conversation-side view displayed both turn states and token values, with running values changing automatically while visible.

At the `0.2.7` validation, that version was installed in the local marketplace. SHA-256 hashes of its manifest, MCP configuration, bundled server, and panel HTML match the source build. A direct stdio call against that installed bundle, with `CODEX_HOME` deliberately absent, returned `verified`, an active turn, zero skipped records, exact observed usage, and zero bytes on an immediate repeat. This installed-bundle check preceded the restarted Desktop observation above.

In a same-file local reconciliation, the original one-shot `profiler.sourceProbe` and the `0.2.7` incremental projection agreed on the latest completed turn's duration, **29** recognized tool completions, input tokens, and output tokens. The incremental scan skipped zero records. This supports the new projection's local correctness; visible Desktop usage reconciliation is still open.

## Resource and privacy baseline

Three active scans of the same approximately 0.68 MB completed rollout took **18, 19, and 19 ms** inside the Node process, with reported peak RSS **42 MiB** in each run. This is a one-shot scanner baseline, not a measurement of continuous live profiling overhead or Codex task slowdown. The scanner has no resident process. The installed MCP App runtime is a bundled stdio server and needs no `npm install`. In a four-second idle sample after startup using the `0.2.1` minified installed bundle, its RSS was **46.2 MiB** at both ends and CPU increment was 0% of one logical CPU. An independent one-shot `0.2.2` source scan of this chat's approximately 10 MB rollout took **200 ms** and reached **85 MiB** process peak RSS. A later one-shot read-only scan of the approximately 14.9 MiB active rollout took **138 ms** and reached **80 MiB** process peak RSS, with 140 ms user CPU and 93 ms system CPU reported by Node. In a 15-second read-only append check on the same file, 5,285 new bytes contained seven complete records, including one token-usage record and one tool-completion record; opening, reading, and parsing just those appended bytes took **1 ms** in that one sample. These exceed the v1 companion/plugin-local 40 MiB idle memory target or resource direction as applicable; one-shot and resident-process measurements are not interchangeable. Re-reading the full rollout for frequent live refresh is therefore an unsuitable default; incremental reads appear feasible but require a bounded implementation and active overhead measurement. The P0 probes do no continuous collection, so these are warnings for future architecture, not silent budget relaxations. Desktop lifecycle and active overhead remain unmeasured. Tests verify that prompt-shaped labels, native IDs, command text, stdout/stderr, and messages are absent from output. No raw rollout or private path is committed.

The `0.2.7` cursor was exercised locally against this chat's approximately **21.1 MiB** active rollout. Initial catch-up took **560 ms** and read 21,055,677 bytes; an immediate second call took **2 ms** and read zero bytes. Its 4 MiB maximum JSONL line size was chosen after counting four `item_completed` lines and two `compacted` lines above 1 MiB; the largest observed line was approximately **2.15 MiB**. With the 4 MiB cap, no records were skipped in that run. A separate one-shot Node process using explicit GC reported **131 MiB** peak RSS and **96 MiB** RSS after GC. The process retains only projected counters and a bounded partial line, but this evidence exceeds the 40 MiB idle direction. It does not establish the bundled Desktop process's steady-state RSS or the five-second panel refresh overhead. Those measurements remain P0 work.

Two further standalone samples used the **installed `0.2.7` stdio server** and Windows process counters. In a 30-second sample, RSS was **58 MiB** after MCP connection, **86 MiB** just after catch-up, and about **53 MiB** after settling. Six five-second progress calls read 0, 0, 3,543, 6,452, 0, and 0 bytes; the rounded process CPU counter stayed unchanged over the last approximately 20 seconds. A second sample separated the Windows counter query from the MCP call: three progress calls took **6, 6, and 5 ms**, reading 0, 0, and 2,775 bytes, while RSS settled near **52 MiB**. These small samples support cheap appended-byte checks but show resident memory above the 40 MiB target. They do not measure Desktop UI rendering or end-to-end Codex turn overhead.

After the Desktop restart, a read-only Windows process check found **three** `node.exe` processes running the installed `0.2.7` bundle under a `codex` parent. One sample showed **45.4, 50.0, and 74.5 MiB** RSS; a later aggregate was **170.5 MiB**. The count remained three over approximately 12 seconds. Their separate host roles are not established, so the total is an observed host-managed footprint, not a per-panel allocation. The highest observed process CPU counter rose by 16 ms over that short interval; this is insufficient to claim an end-to-end overhead percentage. The 40 MiB resource direction is still missed, and the cause of multiple host-managed instances needs investigation before P0 architecture acceptance.

## Architecture decision pending

Keep the P0 MCP App as a small host-capability probe and the rollout scanner read-only. The rollout source provides retrospective and observed active turn, usage, and tool facts. Do not add an independent Codex app-server session and mistake its notifications for the active Desktop conversation. The tested global page did not resolve to this chat's saved rollout; the conversation-side tab did and, in `0.2.7`, displayed changing active values. The Owner has now chosen the conversation-side panel as the v1 primary entrypoint, with the left-navigation page retained as a P0 probe. ADR-0003 records that placement clarification. A standalone dashboard would need explicit chat selection or attachment. Resource compliance and end-to-end overhead remain unproven, especially with three observed host-managed processes. A telemetry companion would be premature while the plugin can read the chat's rollout directly.

### Usage, tools, subagent, and reconnect

Turn usage is frozen to `token_usage_record.turn_token_usage` with explicit turn identity. No `token_count` join is implemented. A read-only replay of one existing native child rollout (`cli_version 0.156.0`) verified the parent/child headers through `session_meta.parent_thread_id`. The child contained six starts, six completions, and six native usage records. Its final usage record identified the completed turn, and all six allowlisted token fields matched the incremental projection. Zero records were skipped and the child file's SHA-256 remained unchanged. This checks projection against the selected native record; it does not provide an independent Desktop-visible usage comparison. The parent sample had no explicit agent lifecycle span, so static lineage does not prove a live parent/child critical path. No child agent was launched for this replay.

A harmless completed shell call in the current chat had status `completed`, exit code `0`, native `item.duration` of 0 seconds plus 563,465,600 nanoseconds, and an envelope start/end timestamp difference of 564 ms. The numeric duration conversion is derived; the native duration object and status are exact reports. Inspection of six October 2–3 rollout files found 27 starts, 25 completions, 2,341 item completions, and no standalone tool-start or explicit retry/reconnect event. Precise live tool-start and model timing remain unavailable through this proven path. Absence in these files does not establish that a provider retry can never be recorded.

The reconnect case closed the installed stdio client, started a fresh installed `0.2.8` server, and reopened this chat using the same metadata. It returned `verified` with zero skipped records and reconstructed the identical latest-completed duration, recognized-tool count, and six token fields. This proves plugin reconnect replay. It is not an induced provider/network retry and makes no claim about Desktop restart behavior.

### Runtime control and candidate sample

A temporary local measurement used Node v24.15.0 and the installed `0.2.8` bundle. Temporary control/measurement files were removed after collecting these sanitized results.

| Condition | Connected RSS after 5 s | Settled RSS | Sample duration | CPU increment / one-core percentage |
| --- | --- | --- | --- | --- |
| Bare MCP stdio SDK control, no profiler | 53.9 MiB | 48.4 MiB | 21,408 ms | 0 ms / 0% at counter resolution |
| Installed thread-only profiler, four 5 s progress requests | 56.7 MiB | 51.7 MiB | 21,558 ms | 31.25 ms / 0.145% |

Do not substitute MCP latency or CPU percentage for end-to-end turn overhead. P0 remains `IN_PROGRESS`, PR draft, independent acceptance pending.
