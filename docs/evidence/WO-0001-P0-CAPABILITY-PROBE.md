# WO-0001 P0 capability probe — partial evidence

Status: **IN_PROGRESS**. This is development evidence, not independent P0 acceptance.

## Tested environment and scope

- Dates: 2026-10-02 to 2026-10-03 (America/Los_Angeles).
- Windows Codex Desktop package: `OpenAI.Codex 26.930.2377.0` during the original panel/source checks; `26.930.3930.0` installed when the `0.2.4` loader failure was diagnosed.
- Codex CLI / rollout `cli_version`: `0.157.0`.
- Probe plugin: `0.2.0` in the first restarted Desktop observation; repaired `0.2.1` in the second; `0.2.2` in the first current-thread source call; `0.2.4` failed to load due to an unsupported manifest field; `0.2.5` restored both placements and read-only current-chat access; `0.2.6` is installed locally to supply a snapshot when the conversation-side panel opens. All are portable local packages with one diagnostic skill, a bundled stdio MCP App, and a Node.js read-only scanner.
- Host: Windows; Node.js `v24.15.0` for the probe. No project-owned daemon, database, listener, network export, or Codex-file write. The MCP server is host-managed stdio and serves a small diagnostic view.
- One previously completed Codex Desktop turn from a local rollout was used. Its native IDs, path, prompts, commands, outputs, account metadata, and raw JSONL are deliberately omitted.

The installed package was listed by `codex plugin list` as enabled. A separate local app-server instance discovered its MCP tool/resource and `thread` entrypoint metadata. After a Desktop restart, `profiler.open` was available and returned successfully; the user screenshot showed a new `Profiler Panel Probe` content tab beside the conversation, but its body was blank. The Desktop log for that open reported `Uncaught SyntaxError: Failed to execute 'write' on 'Document': Invalid or unexpected token` during widget execution. A local syntax check reproduced the error: the build's string replacement expanded `$` sequences in bundled JavaScript and inserted duplicate HTML into it. Version `0.2.1` fixes the replacement, adds a global entrypoint at the user's request, and passes a bundled-script syntax regression test. After the second Desktop restart, the user confirmed the left-navigation entry and reported that opening it displayed the title and status text. The Desktop log recorded successful resource read and `mcp_app_sandbox.widget_running` for the fullscreen global view. A subsequent user screenshot showed the repaired `Profiler Panel Probe` tab rendered beside the conversation with the title and `MCP App opened by the host` status. This proves both supported placements render; it does **not** prove current-thread telemetry access. The screenshot is not committed because it includes unrelated Desktop content.

For `0.2.2`, the tested [Codex `rust-v0.157.0` app-server source](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/app-server/src/request_processors/mcp_processor.rs) adds `_meta.threadId` to direct MCP tool calls. The installed MCP SDK exposes request metadata to the server tool handler. A new `profiler.sourceProbe` tool accepts no thread ID as a model argument: it reads only the host metadata, validates the ID, verifies an exactly matching session header, and returns a content-free rollout summary. Local stdio integration tests pass for supplied request metadata and the missing-metadata case. An independent read-only call against this chat's active rollout matched the session and recovered a completed turn from an approximately 10 MB file in 200 ms, with 85 MiB one-shot process peak RSS. A real Desktop call returned `probe_version: 2`, `thread_context: provided`, `rollout_match: codex_home_unavailable`, and no turn summary. Thus Desktop-to-plugin current-thread metadata transfer **is verified**, while the plugin process lacked the rollout root. The tool does not update the UI or subscribe to live events.

The earlier [Codex `rust-v0.157.0` MCP configuration parser](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/codex-mcp/src/plugin_config.rs) inspection suggested `env_vars`, but that was the **wrong configuration boundary** for the installed Desktop plugin loader. After the user restarted with `0.2.4`, the left-navigation entry disappeared. The Desktop log reported `failed to parse plugin MCP server` and `unknown field env_vars, expected one of command, args, env, cwd`; a subsequent resource read reported `unknown MCP server 'panel-probe'`. This directly explains the missing entrypoint. The successful `codex plugin add` operation did not validate the runtime loader's schema.

Version `0.2.5` removes `env_vars`. When `CODEX_HOME` is absent, the bundled server derives Codex Home from its own `plugins/cache` installation path before verifying a matching rollout session header. This depends on the observed local cache layout and must be reassessed if packaging changes. A copied-bundle stdio integration test under a simulated install path passes with `CODEX_HOME` removed. After restart, the user's screenshot confirmed the global page rendered; its source check returned `thread_context: provided`, `rollout_match: not_found`. A direct tool call from this chat returned `rollout_match: verified` and a completed-turn summary; after opening the conversation-side tab, the user clicked its check button and reported `verified`. Therefore the read-only source path works in the chat context, while the global page cannot be assumed to select that chat. Version `0.2.6` sends the sanitized snapshot in the `profiler.open` result for immediate rendering beside the chat and retains a refresh button. After restart, the real chat-originating open returned `verified` with a completed turn and exact duration quality; the user confirmed the conversation-side panel displayed latest completed-turn duration, tool count, and input/output tokens **before Refresh**. The Desktop log recorded `mcp_app_sandbox.widget_running`. Ten local tests pass. This proves retrospective snapshot rendering; continuous live updates remain unverified.

## Resource and privacy baseline

Three active scans of the same approximately 0.68 MB completed rollout took **18, 19, and 19 ms** inside the Node process, with reported peak RSS **42 MiB** in each run. This is a one-shot scanner baseline, not a measurement of continuous live profiling overhead or Codex task slowdown. The scanner has no resident process. The installed MCP App runtime is a bundled stdio server and needs no `npm install`. In a four-second idle sample after startup using the `0.2.1` minified installed bundle, its RSS was **46.2 MiB** at both ends and CPU increment was 0% of one logical CPU. An independent one-shot `0.2.2` source scan of this chat's approximately 10 MB rollout took **200 ms** and reached **85 MiB** process peak RSS. A later one-shot read-only scan of the approximately 14.9 MiB active rollout took **138 ms** and reached **80 MiB** process peak RSS, with 140 ms user CPU and 93 ms system CPU reported by Node. In a 15-second read-only append check on the same file, 5,285 new bytes contained seven complete records, including one token-usage record and one tool-completion record; opening, reading, and parsing just those appended bytes took **1 ms** in that one sample. These exceed the v1 companion/plugin-local 40 MiB idle memory target or resource direction as applicable; one-shot and resident-process measurements are not interchangeable. Re-reading the full rollout for frequent live refresh is therefore an unsuitable default; incremental reads appear feasible but require a bounded implementation and active overhead measurement. The P0 probes do no continuous collection, so these are warnings for future architecture, not silent budget relaxations. Desktop lifecycle and active overhead remain unmeasured. Tests verify that prompt-shaped labels, native IDs, command text, stdout/stderr, and messages are absent from output. No raw rollout or private path is committed.

## Architecture decision pending

Keep the P0 MCP App as a small host-capability probe and the rollout scanner read-only. The rollout source provides retrospective turn, usage, and tool facts and grows during an active turn. Do not add an independent Codex app-server session and mistake its notifications for the active Desktop conversation. The user preferred a left-navigation dashboard, but the tested global page did not resolve to this chat's saved rollout. The conversation-side tab did resolve it. Thus the reliable P0 path is opening the profiler from the target chat; a standalone dashboard would need explicit chat selection or attachment. The `0.2.4` manifest failure shows runtime loader compatibility must be tested on each changed package. Live updates and resource compliance remain unproven. A telemetry companion would be premature while the plugin can read the chat's rollout directly. No ADR change is proposed from this partial sample.
